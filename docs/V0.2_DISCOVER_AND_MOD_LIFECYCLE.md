# v0.2 — Discover and Mod Lifecycle Design

## 1. Discover page responsibility

Discover is a remote catalog, not a second file manager. Its job is to answer four questions quickly:

1. What packages are available for How to Fish?
2. Is this package already installed?
3. Is an update available?
4. What dependencies must be installed with it?

The first implementation uses Thunderstore's community package index for `how-to-fish`. The community is still small enough for a cached full index; the architecture keeps the catalog behind `IModCatalogService` so a future paginated/Cyberstorm implementation can replace it without changing the UI or installer.

### Layout

```text
Discover
Search...                  Category        Sort        Refresh
-------------------------------------------------------------
N packages

[ package card ]   [ package card ]
[ package card ]   [ package card ]
```

Each card exposes only the information needed for a decision:

- package name;
- author;
- up to two categories;
- latest version;
- aggregate downloads;
- short description;
- Install / Update / Installed state;
- Open page.

Remote README rendering and image-heavy hero cards are intentionally excluded from v0.2.

## 2. Catalog lifecycle

```text
Open Discover / Check updates
        |
        v
15-minute cache fresh? ---- yes ---> read cache
        |
       no
        v
Thunderstore HTTP index
        |
        +---- success ---> cache JSON ---> render
        |
        +---- failure ---> stale cache if available
```

Network access is lazy. Merely launching HTF Manager does not download the catalog.

## 3. Local import pipeline

```text
ZIP / DLL
   |
   v
Inspector (read-only)
   |
   +-- reject unsupported/unsafe package
   |
   v
Install plan
   |
   v
Dependency check
   |
   v
Conflict check
   |
   v
Staging directory
   |
   v
Transactional copy + backup
   |
   v
Ownership record
   |
   v
Refresh Mods page
```

The Inspector never executes an imported DLL. Direct DLL inspection uses PE/.NET metadata to confirm that the assembly references BepInEx.

## 4. Installation routing

Recognized archive paths:

```text
BepInEx/plugins/...  -> Game/BepInEx/plugins/...
plugins/...          -> Game/BepInEx/plugins/...
BepInEx/config/...   -> Game/BepInEx/config/...
config/...           -> Game/BepInEx/config/...
BepInEx/patchers/... -> Game/BepInEx/patchers/...
patchers/...         -> Game/BepInEx/patchers/...
```

A simple archive without an explicit BepInEx root is isolated under:

```text
BepInEx/plugins/<PackageName>/...
```

This supports simple DLL packages and How to Fish content folders such as `Maps/` without scattering arbitrary files across `plugins/`.

## 5. Protected paths

The normal installer does not write to:

- `How to Fish.exe`;
- `How to Fish_Data/`;
- `MonoBleedingEdge/`;
- `UnityPlayer.dll`;
- `BepInEx/core/`;
- any path outside the game directory.

BepInEx runtime maintenance should be implemented as a separate explicit loader-management flow, not as a normal Mod install.

## 6. Ownership model

Every package installed by HTF Manager gets a record with:

- internal ID;
- game directory;
- name / author / version;
- source type;
- Thunderstore package key when known;
- dependencies;
- SHA-256 of the source package;
- managed file paths;
- package-declared user-data/config paths.

This makes uninstall deterministic. The manager never scans a folder and guesses what should be removed.

### External mods

Plugins that existed before HTF Manager ownership are shown as `External / Manual`.

Allowed:

- inspect;
- enable;
- disable;
- open folder.

Not automatically allowed:

- uninstall;
- overwrite;
- update.

A future adoption workflow should snapshot an external package explicitly before allowing destructive actions.

## 7. Enable / disable

Managed package state is applied to all owned loadable DLLs:

```text
Enabled:  Foo.dll
Disabled: Foo.dll.disabled
```

Changes are blocked while How to Fish is running and take effect on the next game launch.

Assets/config files are not renamed when a package is disabled.

## 8. Update

### Thunderstore-managed update

```text
Installed PackageKey + version
        |
        v
Catalog latest version
        |
        v
Resolve dependencies
        |
        v
Download ZIP to cache
        |
        v
Run the same local installer
        |
        v
Preserve previous enabled state
```

The update path is deliberately the same installer used for local ZIPs. Remote sources do not get a privileged write path.

### Manual update

Dragging a newer archive with the same package identity/name reuses the existing ownership record and updates its managed files. Obsolete manager-owned non-config files are removed after the new package stages successfully.

## 9. Uninstall

Managed uninstall removes only recorded managed files. Package-declared/user-created config data can be preserved according to Settings.

```text
Managed files       -> delete
Config/user data    -> preserve by default
Empty plugin dirs   -> prune
Ownership record    -> remove
Package cache       -> keep unless user cleans cache later
```

## 10. Dependency resolution

Thunderstore dependency strings use the package identity and version in a form similar to:

```text
Namespace-PackageName-1.2.3
```

The manager:

1. treats an already healthy BepInEx installation as satisfying BepInEx-pack dependencies;
2. checks currently installed package keys;
3. loads the catalog only when needed;
4. recursively installs missing dependencies before the requested package;
5. stops circular recursion with a visited set.

## 11. UI states

Installed Mods should distinguish:

- External / Manual;
- Local archive;
- Local DLL;
- Thunderstore;
- Development.

A managed Thunderstore package can show `Update available`. External packages deliberately do not claim that state unless a future adoption/matching workflow proves their identity.

## 12. Next iteration

The logical v0.3 additions are:

- explicit Package Inspector review dialog before local auto-install;
- detailed Mod inspector pane with dependency/file ownership views;
- file verification hashes;
- external Mod adoption;
- version selection / downgrade;
- native BepInEx `.cfg` editor;
- Profile export/import with version locking;
- Nexus adapter behind the same catalog/download contracts.
