# v0.3.5 Portable Profiles

## Goal

A profile should be shareable between HTF Manager installations without copying game files or redistributing third-party Mod binaries.

## File format

The `.htfprofile` extension is a ZIP container owned by HTF Manager.

Typical contents:

```text
My-Coop.htfprofile
├─ manifest.json
└─ configs/
   ├─ 01ab...cfg
   └─ 92cd...cfg
```

`manifest.json` uses format id `HTFManager.Profile` and schema version `1`.

## What is shared

- Profile name.
- Required Mod references.
- Required Mod versions as informational metadata.
- Loader/component/source metadata.
- Enabled/disabled state.
- Thunderstore package keys where known.
- Optional Mod configuration snapshots created by v0.3.4.

## What is not shared

- DLL files.
- Mod ZIP packages.
- BepInEx or MelonLoader binaries.
- Loader-wide configuration such as `BepInEx.cfg` or `Loader.cfg`.
- Game files.

## Import lifecycle

```text
.htfprofile
    ↓
read ZIP without extraction
    ↓
validate manifest / paths / limits / SHA-256
    ↓
match Mod references to currently installed Mods
    ↓
show import preview
    ↓
create a new local profile
    ↓
store unresolved requirements separately
    ↓
copy only validated configuration snapshots to profile-snapshots/
```

## Missing Mods

Missing Mods are represented by `ProfileModRequirement` entries rather than fake local Mod ids.

A profile with unresolved requirements is intentionally not applicable. This prevents a shared environment from silently starting with part of its Mod set missing.

After the user installs a missing Mod, `Resolve again` retries matching. If a requirement is no longer wanted, it can be removed from the profile without touching the installed Mod library.

## Configuration association

Each exported configuration snapshot is linked to a portable Mod id. Imported configurations are only restored after their owning Mod is resolved locally.

The importer currently accepts only Mod-specific paths under:

```text
BepInEx/config/
```

and rejects the loader-wide:

```text
BepInEx/config/BepInEx.cfg
```

This is intentionally conservative.

## Next architecture step

v0.3.6 should build a Profile Restore Assistant on this metadata. Known Thunderstore `PackageKey` requirements can be resolved against Discover and installed through the existing Package Inspector / dependency / ownership pipeline. Unknown local, Nexus or external requirements should remain manual until a trusted provider exists.
