# v0.3.8 Scope Lock

## Release name

**HTF Manager v0.3.8 — Version Reconciliation & Application Delivery**

v0.3.8 turns the `VersionMismatch` state introduced in v0.3.7 into an explicit, ownership-safe workflow and establishes the first normal-user Windows distribution/update path.

## Version reconciliation contract

For a deterministic profile requirement where the installed Mod has a different version, the user may explicitly choose one of three outcomes:

1. **Restore expected version** — locate the exact profile-expected artifact, inspect it, then use the existing transactional installer to replace the currently managed version.
2. **Accept installed version** — update only that profile expectation to the deterministic installed version.
3. **Leave unchanged** — preserve the visible `VersionMismatch` state.

There is no silent downgrade, upgrade, baseline rewrite, or automatic bulk reconciliation.

### Exact-source priority

For `Restore expected version`, resolution order is:

```text
Exact payload from the active imported .htfbundle
→ exact verified retained package-history artifact
→ exact Thunderstore PackageKey/version
→ Manual
```

Version fallback is not allowed in reconciliation. If the profile expects `1.2.0`, an available `1.3.0` is not an acceptable substitute.

Provider `PackageKey` remains stronger than `IntrinsicId`. A provider-backed requirement must not fall back to a local intrinsic identity. A local deterministic requirement may use `IntrinsicId` only when no provider key exists.

## Versioned artifact history

v0.3.8 extends package retention from the currently installed source artifact into a verified version history under HTF Manager's local data directory. Historical artifacts are keyed by deterministic identity, exact version, logical source, SHA-256, and file size.

Before a managed replacement, HTF Manager attempts to preserve the current verified source artifact. After a successful installation, the new verified source is captured as another history record when package caching is enabled.

Historical package files are never reconstructed from live game directories. A corrupt/missing historical file is ignored rather than trusted from metadata alone.

A Full `.htfbundle` export may use an exact historical artifact for the profile-expected version even when the sender currently has another version installed. The current drift never changes the profile's desired version.

## Transaction and configuration invariants

Version replacement reuses the existing Package Inspector and transactional Mod installer. The installer owns the actual file replacement/rollback behavior. Package-owned files from the previous version are removed when absent from the target version; configuration/user-data paths remain preserved according to the existing installer policy.

The user must see Package Inspector before the replacement is committed. Health is refreshed after a successful replacement.

## Accept-installed semantics

`Accept installed version` is allowed only when:

- health is `VersionMismatch`;
- the installed version is known;
- expected and installed deterministic identity match under the same strong-identity rules.

The action changes the profile's expected version and local binding metadata. It must not fabricate a provider key or take ownership of an external/manual Mod.

## Application delivery

v0.3.8 introduces the first supported normal-user Windows build:

```text
HTFManager.exe
RID: win-x64
.NET 10 self-contained
single-file
not trimmed
```

The release helper also generates:

```text
update-manifest.json
SHA256SUMS.txt
```

The stable executable asset name is intentionally `HTFManager.exe` so future self-updates can replace the running application without encoding a stale version into the target filename.

## Software update contract

The updater uses the public GitHub Releases `latest` endpoint as the stable update catalog. v0.3.8 supports:

```text
explicit/periodic check
→ validate stable manifest
→ stream executable download
→ validate size + SHA-256
→ stage under %LOCALAPPDATA%\HTFManager\updates
→ explicit Restart and update
→ temporary copy of current EXE acts as update host
→ wait for main process exit
→ backup old EXE
→ replace target
→ launch new EXE
→ rollback replacement when update application fails
```

Startup checks are throttled to at most once per 24 hours unless the user explicitly chooses **Check now**.

The update system never requires a GitHub token for public releases and never silently downloads/applies an update as a forced operation.

### v0.3.8 updater limitations

The first updater version intentionally does not include:

- UAC elevation for non-writable application directories;
- delta patches;
- Authenticode verification/code-signing infrastructure;
- MSI/MSIX/installer framework;
- beta/prerelease channels;
- forced updates;
- background silent replacement.

If the current executable directory cannot be safely written, HTF Manager keeps the verified download but tells the user to update manually/open the release page.

SHA-256 protects integrity against corruption or mismatch with the release manifest; it is not a replacement for future Authenticode signing.

## GitHub release automation

`.github/workflows/release.yml` runs on version tags and performs restore, Release build, automated tests, win-x64 single-file publish, manifest/hash generation, and release-asset upload. A release tag must match `VERSION`.

## Explicitly out of scope

v0.3.8 does **not** add:

- fuzzy Mod identity matching;
- automatic reconciliation of external/manual Mods;
- bulk `Fix all`/silent downgrade operations;
- dependency-closure version locking;
- Nexus/provider-framework refactor;
- profile auto-Apply after reconciliation;
- installer/desktop shortcut/uninstaller;
- code-signing certificate management;
- delta update packages;
- ARM64 release artifacts.

These are later milestones, not hidden v0.3.8 requirements.
