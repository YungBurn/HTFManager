# HTF Manager v0.3.9 Validation Checklist

## Automated gate

Run on Windows with the .NET 10 SDK:

```powershell
dotnet restore HTFManager.slnx
dotnet build HTFManager.slnx --configuration Release --no-restore
dotnet test --project .\tests\HTFManager.Tests\HTFManager.Tests.csproj --configuration Release --no-build --no-restore
```

Expected test count after this patch:

```text
80 total
80 passed
0 failed
0 skipped
```

The known Avalonia `AVLN3001` warnings for dialog resources may still appear unless addressed separately; they are not introduced by v0.3.9.

## Reconciliation UX smoke test

1. Save a profile while a managed Mod is at version `1.0.2`.
2. Install deterministic version `1.0.3` without accepting it into the profile.
3. Expand the profile.
4. Confirm the Mod row shows both values explicitly:

```text
Expected 1.0.2 · Installed 1.0.3
```

5. Open Profile Health and choose **Restore Expected Version**.
6. Confirm Package Inspector names the resolver provenance (bundle, retained package history, or Thunderstore).
7. Complete replacement and confirm Profile Health returns to `Healthy`.

## Portable bundle wording smoke test

Use a `.htfbundle` whose profile expects `1.0.2` while the machine has `1.0.3` installed and the bundle contains exact `1.0.2`.

Expected import UI:

- the missing-payload counter is explicitly labelled as missing + bundled exact;
- the version mismatch remains counted as a version mismatch;
- that mismatch row indicates that an exact bundle payload is available;
- importing the profile does not automatically install/downgrade anything.

## Update metadata failure tests

Exercise or rely on automated coverage for:

- same-version latest release;
- older latest release;
- release/manifest version mismatch;
- malformed SHA-256;
- unexpected executable asset name;
- non-HTTPS executable asset URL;
- GitHub asset size mismatch;
- HTTP `Content-Length` mismatch;
- body exceeding manifest size;
- final SHA-256 mismatch;
- partial download cleanup.

No failed payload may become a `Ready` staged update.

## Real v0.3.8 → v0.3.9 update test

This test closes the application-update validation deferred from v0.3.8.

1. Keep a copy of the official/published v0.3.8 executable.
2. Publish a stable v0.3.9 release with matching `update-manifest.json`.
3. Run v0.3.8.
4. **Check now** must report v0.3.9.
5. Download the update.
6. Confirm size/SHA-256 verification succeeds.
7. Choose **Restart and Update**.
8. Confirm v0.3.9 launches from the original executable path.
9. Confirm profiles, settings, game path, ownership registry and artifact history remain intact.

Compatibility note: this transition is applied by a temporary copy of the v0.3.8 executable, so it uses the v0.3.8 Update Host implementation. It cannot validate the startup-acknowledgement protocol newly added in v0.3.9.

## v0.3.9 startup-acknowledgement rollback

For updates initiated by v0.3.9, the Update Host now waits for the replacement executable to acknowledge successful application initialization before deleting `HTFManager.exe.old`.

A controlled local fault-injection test should verify that an executable that exits before acknowledgement or never acknowledges causes rollback/relaunch of the old target.

The first **production cross-version** validation of this new protocol requires a release newer than v0.3.9 (for example `v0.3.9 → v0.4.0`).

## Authenticode

Authenticode enforcement is intentionally not part of this patch. If official signing becomes available, integrate signing into the release pipeline before calculating final release SHA-256 values and then add expected-publisher verification as a separate hardening step.
