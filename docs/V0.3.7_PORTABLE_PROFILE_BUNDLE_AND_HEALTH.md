# v0.3.7 Portable Profile Bundle & Health

## Status

Implemented on the v0.3.7 feature branch. The final release candidate adds deterministic local Mod intrinsic identity and promotes application/bundle/profile version metadata to 0.3.7. Final publication still requires the normal local Windows/.NET 10 build/test/runtime validation after applying the release overlay.

This document is the canonical v0.3.7 product/architecture scope. It intentionally separates **health detection and portable bundle restoration** from **version reconciliation**. v0.3.7 may detect `VersionMismatch`, but it must not silently or automatically replace an already-installed different version.

## Product goal

v0.3.7 turns portable profiles into a safer environment-sharing workflow with two explicit share modes:

- **Lightweight share** — export the existing `.htfprofile` only.
- **Full portable share** — export a `.htfbundle`, which is a ZIP-compatible container holding the `.htfprofile` plus eligible Mod package payloads.

A receiving user must always be **profile-first**:

```text
.htfbundle
    ↓
validate container
    ↓
read bundle.json
    ↓
read embedded .htfprofile
    ↓
compare expected profile state with installed environment
    ↓
build a read-only import/recovery plan
    ↓
only after explicit user action may an individual bundled package enter Package Inspector
```

The presence of a Mod payload inside a bundle must never be treated as permission to install or overwrite it automatically.

---

## 1. Canonical desired state: profile expectations

v0.3.6 persists enabled/disabled state and unresolved requirements, but metadata for a successfully matched requirement is not retained as a durable local expectation. This prevents reliable long-term health checks.

v0.3.7 must add a local expectation model for every profile member.

Conceptually:

```text
ModProfile
├─ ExpectedMods            canonical desired inventory
├─ ModStates               resolved apply projection
├─ UnresolvedMods          compatibility/missing projection
└─ ConfigurationSnapshots
```

Each expectation should preserve the original profile requirement metadata plus the currently resolved local Mod ID when known.

Required expectation metadata:

- portable identity;
- name/author for display;
- trusted provider `PackageKey` when available;
- deterministic intrinsic Mod identity when available (for example a BepInEx `BepInPlugin` GUID);
- expected version;
- source;
- loader/component;
- desired enabled state;
- resolved local Mod ID when deterministic;
- metadata quality for migrated legacy profiles.

### Invariant

For a complete v0.3.7 profile:

```text
ExpectedMods = desired profile inventory
ModStates = currently resolved local apply bindings
UnresolvedMods = requirements that currently have no resolved local Mod
```

`ExpectedMods` must not silently change because a user's installed version changes.

---

## 2. v0.3.6 migration behavior

Existing v0.3.6 profiles must continue to load.

### Existing unresolved requirements

`UnresolvedMods` still contains complete requirement metadata. These can become complete expectations with no resolved local ID.

### Existing resolved members

Older profiles may only retain a local Mod ID and enabled state. Their original portable expected version may already have been lost.

v0.3.7 must not invent missing historical metadata.

Use an explicit metadata-quality distinction such as:

- `Complete`
- `LegacyBindingOnly`

A `LegacyBindingOnly` expectation may use the existing local binding for compatibility, but health reporting must make clear that the original expected version cannot be proven.

Do not automatically redefine the current installed version as the historical expected version.

## 3. Read-only Profile Health

Add a pure read-only health service.

Inputs:

```text
ModProfile
+
Installed Mods
```

Output:

```text
ProfileHealthReport
```

Required health states:

- `Healthy`
- `Missing`
- `VersionMismatch`
- `IdentityUncertain`

### Healthy

Trusted identity is present and, when an expected version is known, the installed version matches it exactly under the current conservative version comparison policy.

### Missing

The expected identity is not installed.

### VersionMismatch

Trusted identity is present, but expected and installed versions differ.

v0.3.7 **detects and displays** this state. It does not automatically replace the installed package.

### IdentityUncertain

The application cannot make a deterministic identity/version conclusion. Examples include ambiguous local candidates, unknown installed version where a version is required, or legacy profile metadata that cannot prove the original expectation.

### Matching priority

When a trusted provider `PackageKey` exists, it is stronger than every local identity. When no provider key exists, a deterministic intrinsic Mod identity is stronger than a stale local Mod binding, filename, or display name. For BepInEx packages, v0.3.7 can extract the `BepInPlugin` GUID/name/version through static metadata inspection without loading the untrusted assembly.

The health service must not declare a profile member healthy solely because an old `ResolvedModId` still exists if a stronger provider or intrinsic identity contradicts it. Duplicate intrinsic IDs are `IdentityUncertain`, not a first-match guess.

### Side-effect rule

Health calculation must never:

- install/remove packages;
- change enable state;
- update expected versions;
- rewrite ownership;
- apply a profile;
- alter the game directory.

---

## 4. Apply semantics in v0.3.7

To preserve v0.3.6 behavior while exposing better correctness information:

- `Missing` remains apply-blocking.
- `VersionMismatch` is a visible warning but does not automatically block Apply.
- `IdentityUncertain` is a visible warning but does not automatically block Apply for migrated/legacy compatibility.
- `Healthy` behaves normally.

A later version may add explicit version reconciliation, but v0.3.7 must not silently turn profile health into strict version locking.

## 5. Share modes

The profile sharing UI must expose two clearly different actions.

### Lightweight share

Output:

```text
ProfileName.htfprofile
```

Behavior remains compatible with the current portable profile workflow.

### Full portable share

Output:

```text
ProfileName.htfbundle
```

`.htfbundle` is a ZIP-compatible container with a dedicated extension so it cannot be confused with a normal Mod `.zip` package.

Required root layout:

```text
ProfileName.htfbundle
├─ bundle.json
├─ profile.htfprofile
└─ payload/
   ├─ <portable-id>/
   │  └─ <artifact>
   └─ ...
```

The manifest, not folder naming, defines the relationship between a profile requirement and payload.

---

## 6. What may be bundled

v0.3.7 must be conservative about payload inclusion.

### Eligible candidates

Packages may be included when HTF Manager has a deterministic, inspectable artifact corresponding to the expected requirement, such as:

- a cached Thunderstore package archive;
- a cached/retained HTF-managed local ZIP package with deterministic identity and exact expected version;
- a retained HTF-managed local DLL artifact with deterministic identity and exact expected version where the existing local Package Inspector can inspect it safely.

A local package does not need a Thunderstore page to be bundle-eligible. `PackageKey` remains null for such packages; the bundle/profile carries `IntrinsicId` separately so local provenance is not misrepresented as a remote provider identity.

### Not bundled automatically

The first version must not automatically bundle:

- external/unmanaged Mods discovered in the game directory;
- development/source directories;
- game loaders;
- arbitrary files found by fuzzy search;
- Mod files reconstructed from the live game directory when the original install artifact is not available;
- dependency closure that is not itself an explicit profile member.

If an expected Mod cannot be safely bundled, the full-share summary must classify it as remote-only or manual rather than pretending the bundle is complete.

### Existing pre-v0.3.7 installs

A package installed before artifact retention exists may not have a local artifact. Do not reconstruct it from owned game files in v0.3.7.

It may remain:

- remotely restorable through the current Thunderstore path, or
- manual if no safe source is available.

---

## 7. Package artifact retention

Full portable share requires a stable source artifact. v0.3.7 therefore includes a minimal package-artifact retention layer.

Its responsibility is to retain install-source artifacts that HTF Manager legitimately receives during normal managed installation/preparation flows.

It must not:

- scrape the game directory to recreate packages;
- take ownership of external Mods;
- treat cached artifacts as installed state;
- bypass the existing Mod registry/ownership model.

The cache is a source for future bundle export and local re-inspection, not a second installer.

## 8. Full-share export planning

Before creating a `.htfbundle`, show a read-only export summary.

Example:

```text
18 profile requirements

12 payloads included
 3 remote-only requirements
 2 manual/external requirements
 1 legacy/uncertain requirement

Estimated bundle size: 312 MB
```

The UI must make clear that "Full" means "include every eligible safe local artifact", not "HTF Manager guarantees every third-party Mod can legally or technically be redistributed".

Export must stream payload data into the archive instead of reading all packages into memory at once.

Profile configuration snapshots stay inside `.htfprofile`; they must not be duplicated into payload artifacts.

---

## 9. Bundle import is profile-first

Opening or dropping a `.htfbundle` must never immediately install its payloads.

Required order:

```text
1. Open archive read-only.
2. Validate bundle structure/security limits.
3. Read and validate bundle.json.
4. Read and inspect embedded profile.htfprofile.
5. Compute installed environment health.
6. Match payload metadata to profile requirements.
7. Build an import/recovery plan.
8. Show the user the plan.
9. Import/create the profile only after explicit confirmation.
10. Install a bundled package only when the user explicitly opens Package Inspector for that item.
```

Payload extraction should be lazy. Only the selected payload should be extracted into temporary staging when the user requests inspection.

---

## 10. Recovery source priority

For every expected profile requirement, v0.3.7 uses this decision order:

```text
1. Installed environment
2. Exact bundled payload
3. Existing remote provider path (Thunderstore)
4. Manual/unavailable
```

### Already healthy

If the exact expected Mod/version is already installed:

```text
NoAction
```

The bundled payload is ignored. No duplicate installation occurs.

### Missing + exact bundled payload

Offer:

```text
Inspect bundled package
```

The selected artifact must still pass hash validation and the existing Package Inspector before installation.

### Missing + no bundled payload

Fall back to the existing v0.3.6 Restore Assistant remote/manual planning rules.

### VersionMismatch

Display expected vs installed state. Do not automatically install the bundled expected version in v0.3.7.

This boundary is intentional: replacing an already-installed version is version reconciliation and is not part of this milestone.

---

## 11. Bundled package install path

A bundled payload is only another package source. It is not a new installer.

Required path:

```text
.htfbundle payload
    ↓
lazy extract to temporary staging
    ↓
verify SHA-256 and manifest identity
    ↓
existing Package Inspector
    ↓
explicit user confirmation
    ↓
existing transactional installer / ownership / rollback
    ↓
refresh installed Mods
    ↓
recompute health and restore plan
```

Never extract bundle payload directly into the game directory.

Never auto-apply the profile when restoration completes.

---

## 12. Bundle security contract

All bundle input is untrusted.

v0.3.7 must enforce at least:

- no absolute archive paths;
- no `..` path traversal;
- canonical extraction must remain inside staging;
- reject duplicate critical entries such as multiple `bundle.json` files;
- reject ambiguous/multiple embedded profile entries unless explicitly supported by schema;
- reject symlink/reparse-style archive entries when detectable;
- enforce manifest/profile size limits;
- enforce payload count and total uncompressed size limits;
- enforce per-entry uncompressed size limits;
- validate payload SHA-256 before Package Inspector;
- validate manifest `PortableId`, provider `PackageKey`, local `IntrinsicId`, version and source against the embedded profile expectation;
- clean temporary extraction after completion/cancel/failure.

Hash validation proves bundle integrity, not package trust. Package Inspector remains mandatory.

## 14. Test requirements

v0.3.7 should add a real automated test project if one is not already present.

Priority test groups:

### Profile expectations / migration

- imported exact requirement remains the expected version even when installed version differs;
- captured profile records current deterministic identity/version as expected state;
- export uses expected metadata rather than current drifted installed metadata;
- v0.3.6 unresolved requirements migrate as complete expectations;
- v0.3.6 resolved-only bindings do not fabricate historical expected versions.

### Health

- exact provider or intrinsic identity/version → `Healthy`;
- exact identity/different version → `VersionMismatch`;
- expected identity absent → `Missing`;
- ambiguous local identity → `IdentityUncertain`;
- stale local ID cannot override conflicting trusted `PackageKey`.

### Bundle format / security

- valid bundle manifest/profile parse;
- malformed manifest rejection;
- path traversal rejection;
- duplicate critical entry rejection;
- payload hash mismatch rejection;
- oversized entry/total size rejection;
- bundle payload cannot map to a different requirement identity.

### Recovery planning

- healthy installed package suppresses bundled duplicate install;
- missing + bundled exact → bundled candidate;
- missing + no bundled exact → existing remote/manual path;
- version mismatch never becomes an automatic bundled replacement action;
- bundled candidate enters existing Package Inspector path only after explicit action.

## 16. Explicitly out of scope for v0.3.7

To prevent milestone creep, v0.3.7 must not include:

- automatic version downgrade/upgrade reconciliation;
- "restore expected version" for an already-installed `VersionMismatch`;
- "accept installed version as new profile baseline" workflow;
- batch `Install All`/silent restore;
- Nexus API/login/download integration;
- a large provider registry/framework rewrite;
- fuzzy package-name matching;
- dependency-closure bundling;
- automatic loader bundling;
- automatic external/unmanaged Mod bundling;
- reconstructing packages from live game files;
- persistent imported-bundle cache;
- cryptographic signing/trust infrastructure;
- encryption/password-protected bundles;
- portable profile schema v2 unless a concrete implementation blocker requires it;
- strict SemVer compatibility/pinning;
- automatic profile Apply.

These exclusions are part of the v0.3.7 contract, not optional stretch goals.

## 17. Implementation phases inside v0.3.7

These are phases of one release, not separate future feature versions.

### Phase A — Expected State & Health Foundation

- local profile expectation persistence;
- v0.3.6 migration;
- capture/import/export expectation preservation;
- pure health model/service;
- unit-test project and deterministic health tests.

### Phase B — Artifact Retention & Bundle Schema

- minimal package artifact retention;
- `.htfbundle` schema v1 models/validation;
- bundle security helpers;
- streaming bundle writer/reader foundation.

### Phase C — Share Export

- Lightweight/Full choice;
- full-share eligibility planning;
- `.htfbundle` export;
- summary counts/size;
- no external auto-bundling.

### Phase D — Profile-first Bundle Import

- `.htfbundle` drag/drop/open recognition;
- manifest/profile-only inspection first;
- health + payload availability plan;
- profile import without package side effects.

### Phase E — Bundled Missing-Mod Restore

- lazy payload extraction;
- SHA-256 verification;
- Package Inspector integration;
- existing transactional installer;
- refresh/recompute health after success.

### Phase F — UI/Docs/Release Closure

- Profiles health UI;
- share/import localization;
- documentation and handoff;
- final Windows/.NET 10 validation;
- only then promote version metadata to `0.3.7`.

## 18. Definition of done

v0.3.7 is complete only when all of the following are true:

1. A profile retains durable expected identity/version metadata after import/capture.
2. Health can distinguish `Healthy`, `Missing`, `VersionMismatch`, and `IdentityUncertain` without side effects.
3. Lightweight share still exports a valid `.htfprofile`.
4. Full share exports a valid `.htfbundle` with an embedded `.htfprofile` and only eligible payloads.
5. Importing `.htfbundle` reads/validates the profile before any payload installation is possible.
6. A healthy installed Mod is never reinstalled merely because its payload exists in the bundle.
7. A missing Mod with an exact bundled payload can be inspected through the existing Package Inspector and installed through the existing transaction/ownership pipeline.
8. `VersionMismatch` is visible but is not automatically replaced in this release.
9. External/unmanaged Mods are not silently bundled or taken over.
10. Bundle security/path/hash validation is covered by automated tests.
11. Restoration completion does not automatically Apply the profile.
12. Windows/.NET 10 restore/build/run validation passes before release metadata is promoted.
