# v0.3.7 Profile Health & Version Reconciliation

## Status

Planned next milestone after the verified v0.3.6 Profile Restore Assistant baseline.

## Why this is next

v0.3.6 restores requirements that are still present in `ModProfile.UnresolvedMods`. It deliberately preserves the existing matcher behavior: a trusted identity match such as the same Thunderstore `PackageKey` is considered resolved even when the installed version differs from the portable-profile version.

That creates the next correctness gap:

```text
portable profile expects Author-Mod 1.2.0
local machine has Author-Mod 2.0.0
→ identity matches
→ profile is considered resolved
→ original expected version is no longer represented as an active health issue
```

v0.3.7 should make that drift visible and actionable without turning profiles into an implicit, silent package manager.

## Product goal

Give every profile an explicit health view that can answer:

- Are all expected Mods still present?
- Is the installed Mod the same trusted identity that the profile expects?
- Does the installed version match the expected version?
- Can a supported mismatch be reconciled safely through the existing Package Inspector/ownership pipeline?

## Proposed scope

### 1. Persist expected metadata for resolved members

Add a local-only profile expectation model that preserves the imported/captured identity metadata after a requirement has matched a local Mod. It should retain at least:

- portable identity;
- resolved local Mod ID when known;
- name/author for display;
- trusted `PackageKey` when available;
- expected version;
- source;
- loader/component;
- desired enabled state.

Do not overload `UnresolvedMods` to represent healthy members. Keep unresolved requirements focused on apply-blocking missing Mods.

The portable `.htfprofile` manifest can remain schema version 1 unless implementation evidence shows a schema change is required; the missing information already exists in imported manifest requirements. The first migration target is the local `ModProfile` persistence model.

### 2. Add a read-only profile health model/service

Suggested dispositions:

- `Healthy` — trusted identity present and expected version compatible.
- `Missing` — expected identity is no longer installed.
- `VersionMismatch` — trusted identity present but expected and installed versions differ.
- `IdentityUncertain` — only weak/local identity information is available and no deterministic conclusion should be made.

Health calculation must be read-only. It must not install, remove, enable, disable, or apply a profile.

### 3. Surface health in Profiles UI

Each profile should show a compact summary such as:

```text
Healthy 8 · Version drift 2 · Missing 1
```

Opening health details should show expected vs installed metadata and the reason for each disposition.

### 4. Reconcile supported Thunderstore version drift

For a `VersionMismatch` with an exact Thunderstore `PackageKey`:

1. resolve the exact expected version against the catalog;
2. show expected and currently installed versions;
3. require explicit user action;
4. prepare the selected version through the existing remote package preparation path;
5. enter Package Inspector;
6. rely on existing managed ownership/update safety for replacement;
7. refresh and recompute health after success.

Do not silently downgrade or upgrade. If the currently installed Mod is external/manual or ownership cannot prove a safe replacement, classify the repair as manual rather than taking ownership.

### 5. Migration and compatibility

Existing v0.3.6 profiles must continue to load. The migration must be additive and tolerant of missing expectation metadata. Profiles created before expectation tracking may initially report limited/unknown health until metadata can be reconstructed safely.

## Out of scope for v0.3.7

- Nexus API/login/download integration.
- fuzzy package matching.
- arbitrary local-file search.
- silent version pinning.
- automatic batch downgrade/upgrade.
- automatic profile apply.
- weakening Package Inspector, ownership, loader, or game-running protections.
- full environment lockfiles covering the game/loader/runtime ecosystem.

## Suggested implementation order

1. Define the local expectation and health state models.
2. Define migration/load compatibility for v0.3.6 profiles.
3. Preserve expectations during profile capture/import/resolve operations.
4. Implement a pure read-only health service with deterministic tests.
5. Add Profiles health summary/details UI.
6. Add Thunderstore exact-version reconciliation only after health reporting is stable.
7. Validate update/downgrade ownership behavior with managed vs external Mods.

## Acceptance scenarios

| Expected | Installed | Expected health | Automatic repair eligibility |
|---|---|---|---|
| Thunderstore `A-B` 1.2.0 | `A-B` 1.2.0 | `Healthy` | none needed |
| Thunderstore `A-B` 1.2.0 | `A-B` 2.0.0 managed | `VersionMismatch` | inspect exact 1.2.0 if available |
| Thunderstore `A-B` 1.2.0 | `A-B` 2.0.0 external | `VersionMismatch` | manual unless ownership-safe path exists |
| Thunderstore `A-B` 1.2.0 | absent | `Missing` | existing Restore Assistant path |
| local DLL expected | same local identity/version | `Healthy` when deterministic | none needed |
| local DLL expected | ambiguous candidate | `IdentityUncertain` | manual |

## Later roadmap

After profile health/version reconciliation is stable, a later milestone can introduce a provider abstraction and Nexus integration. That work should plug into restoration/health through trusted provider contracts rather than embedding Nexus-specific behavior into `ProfileService`.
