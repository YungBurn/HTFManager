# v0.3.6 Profile Restore Assistant

## Status

This document defines the v0.3.6 restoration contract and current implementation.

Release status: **implemented and locally verified on Windows with .NET 10**. Restore, Release build, and application startup were confirmed before promoting v0.3.6 to the stable development baseline.

v0.3.6 now includes:

1. the restore behavior contract;
2. the `ProfileRestorePlan` / `ProfileRestoreItem` state model;
3. deterministic Thunderstore `PackageKey + requested version` planning;
4. an explicit-version overload for the existing remote Package Inspector preparation path;
5. a Profiles-page `Restore missing mods` entry point;
6. the Avalonia `ProfileRestoreDialog`;
7. per-item handoff into the existing Package Inspector and install pipeline;
8. automatic local re-match and plan rebuild after each successful install.

The existing v0.3.5.1 profile matching, Package Inspector, dependency, staging, rollback and ownership behavior remains authoritative. Restore Assistant orchestrates those components rather than replacing them.

## Product goal

Turn an imported portable profile with unresolved Mod requirements into a deterministic, inspectable restoration plan without creating a second installer.

```text
portable profile
    ↓
existing local match / ResolveMissingMods
    ↓
unresolved requirements
    ↓
ProfileRestoreService.BuildPlan
    ↓
Ready / VersionFallback / PackageUnavailable / ManualRequired
    ↓
Profile Restore Assistant UI
    ↓
existing Package Inspector
    ↓
existing install pipeline
    ↓
refresh + ResolveMissingMods
    ↓
profile can be applied only when complete
```

## Safety boundary

The restore planner is read-only. Building a plan must never:

- download a package;
- install or remove a Mod;
- install a loader;
- change profile membership;
- apply a profile;
- change enabled state;
- modify configuration snapshots;
- guess a package from a display name.

Restore Assistant uses installable plan items to enter the existing Package Inspector path. Package Inspector remains the confirmation boundary before installation. `VersionFallback` additionally requires an explicit acknowledgement in Restore Assistant before Package Inspector can be opened.

## Trusted automatic provider rule

v0.3.6 automatic restore supports Thunderstore requirements only.

A requirement is eligible for automatic Thunderstore resolution only when both are true:

- `ProfileModRequirement.Source == ModSourceType.Thunderstore`;
- `ProfileModRequirement.PackageKey` is present.

The package must be found by an exact, case-insensitive `RemoteModPackage.FullName == PackageKey` match.

The planner must not use `Name`, `Author`, `FileName`, partial text search, fuzzy search or first-result selection as a substitute for `PackageKey`.

Local archive, local DLL, development and external requirements remain manual in v0.3.6 even if their display metadata resembles a Thunderstore package.

## Version semantics

Portable profile versions remain informational metadata rather than a global hard pin. v0.3.6 uses that metadata to choose the safest restoration candidate without changing existing profile-apply semantics.

### Requested version is present

A requested version is present when `ProfileModRequirement.Version` is non-empty and not `—`.

Resolution order:

1. find the exact package by `PackageKey`;
2. find an exact, case-insensitive `RemoteModVersion.VersionNumber` match after trimming surrounding whitespace;
3. require a non-empty `DownloadUrl` for the version to be considered downloadable;
4. if the exact requested version is downloadable, select it and classify the item as `Ready`;
5. otherwise select the latest downloadable active version;
6. if no active downloadable version exists, select the latest downloadable version regardless of `IsActive`;
7. if a fallback is selected, classify the item as `VersionFallback`;
8. if no downloadable version exists, classify the item as `PackageUnavailable`.

No semantic-version range expansion, upgrade policy or downgrade policy is inferred by the planner.

### Requested version is absent

If no requested version was recorded, the planner selects the latest downloadable version using the same active-first rule and classifies the item as `Ready`.

`Ready` therefore means “a deterministic package/version candidate is available for inspection”, not “install silently”.

### Deprecated packages and inactive exact versions

A deprecated Thunderstore package is not silently replaced with another package.

If the exact requested version is still downloadable, it remains the selected candidate even when the package is deprecated or that version is marked inactive. The item remains `Ready`. The planner records the warning in `ProfileRestoreItem.Message`, and the current Restore Assistant also renders deprecated/inactive warnings from the resolved package/version metadata.

## Restore dispositions

### `Ready`

A deterministic Thunderstore package/version candidate is available.

Typical cases:

- exact requested version found and downloadable;
- no requested version recorded and a latest downloadable version exists.

`Ready` does not bypass Package Inspector.

### `VersionFallback`

The exact requested version is not downloadable, but the same exact Thunderstore `PackageKey` has another downloadable version.

The selected fallback must be shown explicitly to the user before installation. The current UI requires an acknowledgement checkbox before the fallback item can open Package Inspector.

### `PackageUnavailable`

The requirement identifies Thunderstore by source and package key, but restoration cannot currently produce a downloadable candidate.

Typical cases:

- exact `PackageKey` is not present in the current catalog;
- package exists but has no downloadable versions.

The planner must not substitute a similarly named package.

### `ManualRequired`

Automatic restore is not trusted for this requirement.

Typical cases:

- source is not Thunderstore;
- Thunderstore source has no `PackageKey`.

The Restore Assistant exposes the requirement metadata so the user can identify what must be restored manually.

## Plan model

`ProfileRestorePlan` contains only unresolved requirements supplied by the profile at planning time.

It provides counts for:

- total items;
- `Ready`;
- `VersionFallback`;
- `PackageUnavailable`;
- `ManualRequired`;
- total installable candidates.

`ProfileRestoreItem` carries:

- the original `ProfileModRequirement`;
- the restore disposition;
- the exact resolved `RemoteModPackage`, when available;
- the selected `RemoteModVersion`, when available;
- a user-facing planning message;
- computed installability/fallback flags.

The planner deliberately does not mutate `ModProfile.UnresolvedMods`.

## Existing Package Inspector integration

The existing latest-version API remains valid:

```text
PrepareRemotePackageAsync(package)
```

v0.3.6 foundation adds an explicit-version path:

```text
PrepareRemotePackageAsync(package, selectedVersion)
```

The explicit version must belong to that package and have a download URL. It then uses the same existing flow:

```text
DownloadPackageAsync(package, selectedVersion)
    ↓
ModInstallMetadata
    ↓
InspectForInstallAsync
    ↓
PreparedModPackage
```

No installation is performed by the planning service.

## UI and orchestration contract

The current Restore Assistant implementation:

1. runs existing `ResolveMissingMods` before planning;
2. ensures the Thunderstore catalog is loaded and refuses to classify remote requirements when catalog loading fails;
3. calls `ProfileRestoreService.BuildPlan(profile, catalog)`;
4. renders all plan items by `Ready`, `VersionFallback`, `PackageUnavailable`, or `ManualRequired`;
5. allows `Ready` and acknowledged `VersionFallback` items to open Package Inspector with the plan's exact `SelectedVersion`;
6. requires explicit user acknowledgement for `VersionFallback`;
7. relies on the existing Package Inspector for the final install confirmation;
8. refreshes Mods through the existing installer, then runs `ResolveMissingMods` after a successful install;
9. rebuilds the restore plan after each successful restoration;
10. never automatically applies the profile when the last missing Mod is resolved.

## Out of scope for v0.3.6

- Install All / batch installation.
- automatic profile apply.
- strict version pinning of already installed Mods.
- automatic downgrade/upgrade of an already matched Mod.
- fuzzy Thunderstore lookup.
- Nexus provider support.
- local file discovery or arbitrary URL download.
- a second Mod/dependency/loader installer.

## Acceptance scenarios

| Requirement | Catalog state | Expected disposition | Selected version |
|---|---|---|---|
| Thunderstore + PackageKey + `1.2.0` | exact `1.2.0` downloadable | `Ready` | `1.2.0` |
| Thunderstore + PackageKey + `1.2.0` | exact absent, latest `1.4.0` downloadable | `VersionFallback` | `1.4.0` |
| Thunderstore + PackageKey + `1.2.0` | package absent | `PackageUnavailable` | none |
| Thunderstore + PackageKey + `1.2.0` | package present, no downloadable versions | `PackageUnavailable` | none |
| Thunderstore + PackageKey + `—` | latest downloadable `1.4.0` | `Ready` | `1.4.0` |
| Thunderstore without PackageKey | any | `ManualRequired` | none |
| LocalDll / LocalArchive / External / Development | any | `ManualRequired` | none |
| Thunderstore + exact inactive `1.2.0` with download URL | exact present | `Ready` with warning | `1.2.0` |
| Thunderstore deprecated package + exact downloadable version | exact present | `Ready` with warning | requested version |

## Baseline compatibility

The v0.3.6 Restore Assistant implementation remains intentionally additive:

- `ProfileService.MatchRequirement` behavior is unchanged;
- `ResolveMissingMods` behavior is unchanged;
- portable profile schema remains version `1`;
- existing Discover calls to `PrepareRemotePackageAsync(package)` still select `LatestVersion`;
- existing install and ownership logic is unchanged.
