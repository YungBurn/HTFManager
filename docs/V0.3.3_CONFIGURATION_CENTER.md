# v0.3.3 Configuration Center design

## Goal

Complete the normal mod lifecycle by bringing frequently edited loader/mod settings into HTF Manager while preserving the original config files and keeping the feature loader-aware.

## Data flow

```text
GameEnvironment
     |
     +-- BepInEx/config/**/*.cfg
     |
     +-- UserData/Loader.cfg
              |
              v
      ConfigurationService
              |
       parse read-only model
              |
              v
       Configuration page
              |
        user edits values
              |
              v
      validate changed entries
              |
       optional local backup
              |
        temp file + replace
```

The UI never writes configuration text directly. File parsing, validation, backups and writes live in `HTFManager.Infrastructure.Configuration` behind `IConfigurationService`.

## Models

- `ModConfigurationDocument`: one physical configuration file.
- `ConfigurationEntry`: one section/key/value plus optional BepInEx metadata.
- `ConfigurationValueKind`: Boolean, Integer, FloatingPoint, Choice, Text.
- `ConfigurationBackupInfo`: local backup metadata.
- `ConfigurationOperationResult`: save/restore result.

## BepInEx parsing

The service intentionally supports the common generated BepInEx layout rather than implementing a full TOML parser.

Metadata comments such as these are recognized when present:

```text
# Setting type: Boolean
# Default value: true
# Acceptable values: A, B, C
# Acceptable value range: From 0 to 100
```

Sections are keyed as `[Section]` and assignments as `Key = Value`.

Saving preserves all unrelated lines. Only dirty entries are replaced by matching `(section, key)`.

## MelonLoader parsing

`UserData/Loader.cfg` uses the same section + assignment shape required by the generic editor, so it shares the parser while retaining `ModLoaderKind.MelonLoader` metadata.

HTF Manager supplies known choices/defaults for common loader values such as `harmony_log_level` and `theme` so they can use a choice editor.

## Association with installed mods

A config can be linked to a detected mod by comparing normalized tokens from:

1. BepInEx header plugin name;
2. config filename;
3. plugin GUID, when available;
4. installed mod display name;
5. assembly filename;
6. package key / internal mod id.

Association is deliberately conservative. If no useful match is found, the config remains available in Configuration but no Configure button is added to a Mod card.

## Backups

Backups are stored under the manager data directory, not in the game directory:

```text
config-backups/
  <file-stem>-<path-hash>/
    20260828-123456-789.cfg
```

The path hash prevents two different mods with the same config filename from sharing a backup folder.

## UI constraints

The central Configuration workspace is a two-column desktop layout:

```text
+----------------------+-------------------------------------+
| config list          | selected config                     |
| search               | badges / path / actions             |
| loader filter        | section filter                      |
|                      |                                     |
| fixed scroll         | fixed scroll: setting editors       |
|                      |                                     |
|                      | dirty state / discard / save        |
+----------------------+-------------------------------------+
```

No number of config files or settings is allowed to increase the main page's desired height indefinitely.

## Future extension points

The next configuration milestones can add:

- MelonPreferences schema-aware editing;
- per-profile config snapshots;
- config diff / compare;
- explicit mod-provided `htfmanager.json` schemas;
- advanced/developer-only setting groups;
- import/export presets.
