# HTF Manager v0.3.9 Scope Lock

## Release theme

**v0.3.9 — Update Hardening & Reconciliation UX**

v0.3.9 is intentionally a hardening and product-clarity release. It does not introduce a new Mod provider, a new profile format, or automatic Mod version policy. Its primary purpose is to close the real `v0.3.8 → v0.3.9` application-update loop and make v0.3.8 reconciliation behavior easier to inspect.

## MUST

### 1. Cross-version self-update readiness

The release must close the original v0.3.8 deferred validation path:

```text
v0.3.8
→ detect v0.3.9
→ validate update-manifest.json
→ download HTFManager.exe
→ verify declared size + SHA-256
→ stage
→ Restart and Update
→ replace executable
→ launch v0.3.9
→ preserve user data
```

Important compatibility boundary: the temporary Update Host used during `v0.3.8 → v0.3.9` is a copy of the currently running **v0.3.8** executable, so the new v0.3.9 startup-acknowledgement protocol cannot retroactively participate in that first transition. v0.3.9 adds the acknowledgement protocol for updates initiated by v0.3.9 and later.

For v0.3.9-initiated updates, if the replacement executable cannot start or does not acknowledge startup within the timeout, the Update Host must stop it, restore the `.old` executable, and relaunch the previous version.

### 2. Updater input hardening

The stable updater must reject:

- same-version or older releases as updates;
- unsupported manifest schema/channel/RID;
- manifest version that differs from the GitHub release tag;
- unexpected executable asset names;
- non-HTTPS manifest/executable asset URLs;
- invalid SHA-256 metadata;
- invalid or mismatched asset size metadata;
- downloads that exceed the declared manifest size;
- downloads whose final size or SHA-256 differs from the manifest.

Partial `.download-*` files must not remain usable after failure or cancellation. A previously staged executable may be reused only after its size and SHA-256 are revalidated.

### 3. Reconciliation Expected/Installed UX

A profile row with version drift must clearly distinguish the profile baseline from the currently installed version.

Example:

```text
Expected 1.0.2 · Installed 1.0.3
```

The profile UI must not imply that the profile expected version silently changed merely because a different version is currently installed.

### 4. Bundle recoverability wording

Bundle import counters and badges must distinguish:

- a Mod that is missing and has an exact bundled payload; and
- a Mod that is installed at the wrong version while the bundle contains the exact expected payload.

The existing missing-only counter is not redefined as a total payload counter. Its label is clarified instead.

## SHOULD

### Restore-source provenance

When exact-version reconciliation enters Package Inspector, the UI should show which resolver source supplied the exact artifact:

- active portable bundle;
- retained package history;
- Thunderstore;
- manual source when applicable.

This provenance is separate from the package's logical provider metadata.

### Update status detail

Settings should expose useful update metadata such as:

- current version;
- latest version;
- stable channel;
- release publish time;
- executable size;
- current verification state;
- last check time.

## DEFERRED / CONDITIONAL

### Authenticode enforcement

Windows Authenticode signing is being prepared independently. v0.3.9 must not require an Authenticode signature until official release signing is available and the expected publisher identity can be defined without breaking unsigned development/test builds.

When signed distribution is available, signature verification can be added as an additional updater trust layer after the existing manifest/size/SHA-256 checks.

## OUT OF SCOPE

v0.3.9 does not add:

- automatic Mod upgrade/downgrade;
- automatic profile-baseline mutation;
- fuzzy version reconciliation;
- new Mod providers;
- cloud profiles;
- dependency-solver redesign;
- delta application updates;
- Beta/pre-release update channels;
- automatic UAC elevation;
- plugin architecture redesign.

## Release gate

The implementation is not considered validated until it passes:

1. Release build on Windows/.NET 10;
2. all automated tests;
3. published single-file EXE smoke test;
4. real `v0.3.8 → v0.3.9` update detection/download/apply/relaunch test using the v0.3.8 updater;
5. profile/settings/artifact-history preservation check;
6. malformed manifest/hash/size failure checks;
7. reconciliation and bundle wording smoke tests with a real version mismatch;
8. v0.3.9 Update Host startup-acknowledgement rollback test in a controlled local scenario if practical.

Production cross-version validation of the new acknowledgement protocol requires an update **from v0.3.9 to a later release** and is therefore deferred until that later release exists.
