# HTF Manager v0.3.1 — local multi-loader installation and profile UX

## 1. Startup behavior

The shell always navigates to `Home` after construction. Page navigation is intentionally session-only. Existing `LastPage` JSON is tolerated but ignored.

## 2. Profile card model

Profiles are rendered as independent cards in a fixed 540px scroll surface. No profile is expanded by default.

Collapsed card:

```text
Profile Name
12 Mods · 8 Enabled · BepInEx
                         [Apply] [Delete] [Expand]
```

Expanded card adds:

```text
[Installed mod not in profile                    ] [Add]

+-------------------------------------------------------+
| Mod A     BepInEx · Plugin · 1.2.0   [Enabled] [Remove]
| Mod B     MelonLoader · Mod · 0.4.0   [Disabled][Remove]
| ... fixed 220px scroll area ...                       |
+-------------------------------------------------------+
```

Removing a mod from a profile only edits the profile JSON. It never calls the package uninstaller.

Applying a profile still disables installed mods absent from that profile without deleting them.

## 3. Static assembly inspection

Imports never use `Assembly.Load`, `Assembly.LoadFrom`, reflection activation, or mod code execution.

The inspector uses `PEReader` + `MetadataReader` and walks type base references to identify:

- `BepInEx.BaseUnityPlugin`;
- `MelonLoader.MelonMod`;
- `MelonLoader.MelonPlugin`.

Local inheritance inside the imported assembly is followed recursively until an external base type is reached.

## 4. Direct DLL plans

```text
BepInEx BaseUnityPlugin
  -> BepInEx/plugins/<safe package name>/<dll>

MelonMod
  -> Mods/<dll>

MelonPlugin
  -> Plugins/<dll>
```

A DLL referencing a loader but exposing no recognized entry type is rejected rather than guessed.

## 5. ZIP plans

The ZIP inspector performs these steps:

1. remove one wrapper directory when the archive has a single root folder;
2. read optional Thunderstore `manifest.json`;
3. inspect managed DLL metadata inside the archive;
4. infer one loader;
5. reject archives containing both BepInEx and MelonLoader entry assemblies;
6. preserve explicit loader paths;
7. create an install plan;
8. validate every target path before staging.

### BepInEx targets

Allowed:

```text
BepInEx/plugins/
BepInEx/config/
BepInEx/patchers/
```

### MelonLoader targets

Allowed:

```text
Mods/
Plugins/
```

Normal packages cannot write loader binaries, `MelonLoader/`, `UserData/`, game executable files, or arbitrary root paths.

## 6. Lifecycle reuse

Both loader types reuse the same transaction system:

```text
Inspect -> Plan -> Conflict check -> Stage -> Backup -> Commit -> Ownership
                                      \-> failure -> Rollback
```

Managed loadable DLLs under BepInEx, `Mods/`, and `Plugins/` all participate in enable/disable state and update state preservation.

## 7. Loader readiness

The game must be detected before import. After inspection:

- BepInEx package requires a healthy BepInEx environment;
- MelonLoader package requires a healthy MelonLoader environment.

The manager does not install or switch loaders in v0.3.1.
